# AIPDF 统一研究流程

## 1. 文档地位

本文是 AgentInsight × eufy 项目的统一业务流程说明，用于衔接：

- 行业机会研究：从智能家居市场与真实用户证据中发现值得验证的问题；
- AIPDF 多智能体规范：用职责分离、结构化输出、证据门禁和红队返工验证机会；
- 飞书协作：让用户在 Aily 中发起研究、确认范围、处理阶段决策并沉淀最终提案；
- Package Risk Intelligence Demo：对晋级场景做一次可运行、可失败、可复盘的落地实验。

若其他项目文档对研究范围、候选场景或流程阶段的描述与本文冲突，以本文、`docs/state-machine.md`、`docs/api/openapi.yaml` 和 `docs/acceptance-criteria.md` 的最新版本为准。

## 2. 核心研究问题

> 北美家庭安防中，哪些高频家庭事件目前只能被设备检测和通知，却仍需要用户手动结合事件状态、家庭状态与外部环境完成判断；eufy 是否能将其中一个事件升级为具有风险或价值判断和行动建议的事件理解体验？

本项目不预设门铃包裹场景一定值得立项。系统必须先完成行业机会研究、候选场景比较、证据与可行性评分、红队挑战和人工晋级，才允许进入 Demo。

## 3. 研究范围

| 维度 | 当前范围 |
|---|---|
| 地区 | 北美，优先美国 |
| 行业 | 智能家居，优先家庭安防 |
| 品类 | 视频门铃、室外摄像头、家庭安防中枢及相关软件体验 |
| 目标用户 | 北美家庭安防用户；首个重点细分为经常网购、白天可能无人在家的家庭 |
| 用户标签 | 一户建、双职工、独居、老人家庭、儿童家庭、宠物家庭、租房用户等，可多标签并存 |
| 重点品牌 | eufy、Ring、Google Nest；按证据需要补充 Arlo、Aqara、Apple Home 等 |
| 时间 | 最近两至三年的产品、评价、官方支持资料和公开信息 |
| 排除 | 扫地机器人、整个 eufy 生态重构、安全关键自动处置、人脸身份承诺和无证据市场预测 |

租房用户保留为可验证细分，不再作为整个项目的唯一研究对象。安装、迁移、订阅与权限问题可以进入用户痛点池，但只有与事件理解机会直接相关或在候选评分中胜出的内容才进入本轮产品定义。

## 4. 从行业机会到门铃 Demo 的逻辑

```text
智能家居行业机会
→ 家庭安防被识别为重点研究品类
→ 识别现有产品停留在“检测并通知”的环节
→ 找出用户仍需手动组合的事件状态与上下文
→ 形成适合事件理解的高频家庭事件候选池
→ 比较包裹、车库门、陌生人徘徊等候选场景
→ 按证据、用户价值、竞品缺口、技术、商业和 Demo 可行性评分
→ 红队挑战证据与“伪事件理解”风险
→ 用户在飞书完成候选场景晋级审批
→ 晋级场景进入可运行 Demo
→ 成功才形成上架建议；失败则不建议立项或提出补研条件
```

门铃包裹风险是首选 Demo 候选，而不是行业研究的预定结论。它的优先级来自待验证的工程假设：基础事件清晰、上下文数据相对容易获得、风险低于安全关键场景、行动建议易于解释，并能直观展示“普通通知”与“事件理解”的差异。

## 5. 事件理解判定

一个合格的 Innovation 必须同时包含：

```text
Base Event
+ Event State
+ 至少两个 Context Signals
+ Inference
+ Risk or Value
+ Recommended Action
```

只有人员、包裹、宠物或跌倒识别，不构成事件理解；简单叠加多个通知，也不构成事件理解。

统一表达为：

```text
Event → State → Context → Inference → Risk/Meaning → Action
```

## 6. 候选场景池

候选场景必须来自真实用户证据与竞品能力缺口。以下内容仅用于建立比较框架，不代表已经成立。

| 候选场景 | Base Event | 可验证的 Event State | 候选上下文 | 待验证的判断与行动 |
|---|---|---|---|---|
| Package Risk Intelligence | 包裹送达 | 包裹持续留在门口 | 天气、家庭在家状态、预计回家时间 | 判断包裹受损或长时间暴露风险，提前提醒处理 |
| Garage Door Risk | 车库门打开 | 异常持续开启 | 时间、家庭状态、车辆状态 | 判断是否为遗忘或异常开放，建议关闭或确认 |
| Loitering Context | 门口检测到人员 | 持续或重复停留 | 配送记录、熟悉访客、时间段 | 区分正常经过与需关注的持续徘徊，建议查看或确认 |

系统可以根据真实证据替换候选，但进入候选比较的数量不得少于三个。最终允许一个、多个或零个场景晋级。

## 7. 候选评分

评分不能由模型直接给出一个无依据总分。每项分数必须保存依据、Evidence IDs、计算方法和置信度。

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 用户痛点严重度 | 15% | 问题是否产生明确损失、焦虑或额外操作 |
| 使用频率 | 10% | 目标用户是否会重复遇到该事件 |
| 证据强度 | 15% | 是否有多来源、可回溯且范围匹配的证据 |
| 竞品差异化 | 15% | 市场是否停留在事件链的更低层级 |
| 事件理解完整度 | 15% | 是否满足 Event、State、Context、Inference、Risk、Action |
| 技术与数据可行性 | 10% | 数据源、授权、延迟、准确度与回退是否可接受 |
| 商业与战略价值 | 10% | 是否改善购买、留存、生态或差异化价值 |
| Demo 可行性 | 10% | 是否能用真实或合规模拟数据清晰验证 |

红队可以调低任何维度、要求补研、要求修改或阻止候选晋级。人工审批不能将没有有效证据或不满足事件理解结构的候选强行晋级。

## 8. 飞书在流程中的位置

飞书不是行业判断或产品评分节点，而是贯穿研究流程的入口、协作层、人工决策门和结果出口。

```text
用户在飞书 Aily 提出模糊研究问题
→ Aily 追问并生成结构化 Research Brief
→ 用户确认研究范围
→ Aily 调用 AgentInsight 后端创建项目
→ 后端运行行业机会研究与候选场景比较
→ 飞书推送进度、证据覆盖、候选场景和红队意见
→ 用户在飞书完成候选场景晋级审批
→ 后端运行晋级场景 Demo
→ 飞书展示实验结果并发起最终审批
→ 飞书文档沉淀最终提案或不建议立项结论
```

飞书各能力的边界：

| 飞书能力 | 职责 | 不负责 |
|---|---|---|
| Aily | 澄清意图、生成 Brief、调用稳定 API Skill、查询结论 | 不在 Prompt 中替代后端完成整项研究 |
| 机器人与卡片 | 推送进度、风险和待处理决定，接收人工操作 | 不保存业务唯一状态 |
| 多维表格 | 展示项目、Evidence、Innovation 与 Decision 摘要 | 不作为 Evidence Lake 或 Checkpoint 真相来源 |
| 飞书文档 | 沉淀最终提案、证据目录、限制和审批结论 | 不绕过 Claim Gate 补写事实 |

Deep Research Web 负责复杂过程可视化和证据下钻；飞书负责轻量协作和决策。后端数据库与工作流 Checkpoint 是业务状态的唯一真相来源。

## 9. 端到端业务流程

1. 用户在 Aily 提交模糊研究目标。
2. Aily 补齐市场、用户、品类、品牌、时间、来源和 Innovation 约束。
3. 用户确认 Brief，Aily 调用后端创建项目。
4. 调研总管生成结构化研究计划。
5. 用户研究 Agent 与竞品 Agent 并行运行并共享 Evidence Lake。
6. 证据门禁检查覆盖率、引用、冲突、来源多样性和失败来源。
7. 产品技术 Agent 生成至少三个事件理解型候选。
8. 商业 Agent 对候选进行有依据的结构化评分。
9. 红队攻击证据、竞品、事件理解真实性、技术、商业和隐私风险。
10. 调研总管整合评分、红队调整和未知项。
11. 飞书展示候选比较并等待人工晋级决定。
12. 晋级候选运行可复现 Demo；未晋级候选保留理由。
13. Demo 结果进入最终评估与飞书人工审批。
14. 系统生成“建议立项”“补充验证”或“不建议立项”，并在飞书文档与 Web 报告中沉淀。

## 10. Package Risk Intelligence Demo 边界

若 Package Risk Intelligence 通过场景晋级门，首个 Demo 使用：

```text
包裹送达
+ 包裹仍在门口
+ 家庭无人
+ 预计降雨或其他可验证外部风险
→ 判断包裹可能在家庭成员处理前受损或持续暴露
→ 提前提醒用户取件、联系家庭成员或安排代收
```

Demo 必须明确：

- 包裹事件与状态来自真实设备、授权视频或可标识的合规模拟输入；
- 天气、家庭状态和预计回家时间分别记录数据来源、更新时间和置信度；
- 风险计算由可测试的确定性规则或受控模型完成；
- LLM 只解释已经形成的结构化判断，不单独决定风险；
- 任一关键上下文缺失时降级为不确定或普通提醒；
- 不将“包裹暴露”直接描述为“盗窃”，不承诺身份识别；
- Demo 成功只能证明限定输入和条件下的可行性，不能替代真实用户与规模化验证。

## 11. 最终结论类型

最终输出必须是以下三类之一：

- `recommend`：证据、差异化、数据、技术、商业和红队门禁均通过，建议进入下一阶段产品验证；
- `investigate`：存在价值信号，但关键证据或可行性仍不足，给出补研任务和通过条件；
- `do_not_recommend`：核心痛点、差异化、数据可得性、风险或商业价值不成立，明确不建议立项。

系统禁止为了展示效果强行推荐候选，也禁止将 Demo 可运行等同于产品已经具备上架条件。
